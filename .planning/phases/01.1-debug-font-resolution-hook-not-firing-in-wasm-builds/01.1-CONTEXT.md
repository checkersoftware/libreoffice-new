# Phase 01.1: Debug Font Resolution Hook Not Firing in WASM Builds - Context

**Gathered:** 2026-02-10
**Status:** Ready for planning

<domain>
## Phase Boundary

Fix the WASM font resolution hook so it actually fires at runtime. The hook was implemented in Phase 1 but is not working — the JS callback never triggers, fonts render with fallbacks, and the WASM runtime aborts with an uncaught exception.

</domain>

<decisions>
## Implementation Decisions

### Build Environment
- The WASM build IS configured with `--enable-emscripten-jspi` (JSPI is enabled)
- `HAVE_EMSCRIPTEN_JSPI=1` in the production/test build
- `EM_ASYNC_JS` is the CORRECT path for this build — the sync fallback is secondary
- The Electron app builds LibreOffice into WASM with a specific flag set (see full flags below)

### Target Host
- Electron app only — no browser-only deployment
- The Electron app defines `Module.resolveSystemFont` which should be called by EM_ASYNC_JS
- Host callback currently logs "HALLO ${familyName}" but is never reached

### Observed Symptoms (Updated 2026-02-10 from runtime diagnostics)
- Fonts render with fallback/wrong fonts (not the requested ones)
- `Module.resolveSystemFont` JS callback is never called (no "HALLO" output)
- WASM runtime throws uncaught exception / "Aborted" error (separate from font issue — caused by OOX StorageBase missing input stream)
- **Root cause identified from runtime log:** `bHaveSubstitute=1` for ALL fonts — fontconfig always finds a substitute (e.g., "Segoe UI" → "Liberation Sans"), so the `if (!bHaveSubstitute)` gate at the WASM resolution block is NEVER true. The `em_resolveFontFromHost` JS function is never called.
- The JSPI/ASYNCIFY hypothesis (Research Root Causes 1-3) was NOT the primary issue — the code path never even reaches the EM_ASYNC_JS call

### Root Cause (Confirmed)
**Fontconfig always provides a substitute, blocking the WASM hook.** The original code gated on `!bHaveSubstitute`, but fontconfig has substitution rules for every requested font. Even "Segoe UI" (not bundled) gets mapped to "Liberation Sans" (bundled), making `bHaveSubstitute=1`. The WASM resolution block was dead code.

### Fix Applied
- Changed gate condition from `!bHaveSubstitute` to `!s_pFontCollection->FindFontFamily(rFontSelData.maTargetName)` — checks actual font availability in the collection, not fontconfig's substitution result
- Moved the WASM block to BEFORE `GetFcSubstitute()` so JS resolution happens first
- On successful registration, returns `false` so the caller finds the font directly via `ImplFindFontFamilyBySearchName()`
- Removed the fontconfig retry logic (unnecessary — caller finds font directly in collection)

### JSPI Strategy
- JSPI is ALWAYS enabled — `EM_ASYNC_JS` is the ONLY path, no conditional needed
- Do NOT add `#if HAVE_EMSCRIPTEN_JSPI` / `#else` branching — there is no non-JSPI build
- Do NOT add a sync `EM_JS` fallback — not needed, only the Electron app uses this
- The `#include <config_emscripten.h>` is NOT needed since there is no JSPI conditional

### FS Export
- The Electron app's build process handles FS export — do NOT modify `EMSCRIPTEN_INTEL_GCC.mk`
- No changes to the LibreOffice build system are needed for FS

### Debug Code
- KEEP all debug fprintf and console.warn statements — still actively debugging
- The hook is not firing and the root cause is unknown — debug output is essential
- Do NOT remove debug code until the actual root cause is found and fixed

<specifics>
## Specific Ideas

- **Root cause found:** `bHaveSubstitute=1` always — fontconfig always finds a substitute, blocking the WASM block
- **Fix applied:** Gate on `FindFontFamily()` (actual collection presence) instead of `!bHaveSubstitute`
- The abort ("libc++abi: terminating") is a SEPARATE issue — caused by `StorageBase::StorageBase - missing base input stream` in the OOX filter, NOT related to font resolution
- The Electron `printErr` handler at `libreoffice-wasm.ts:107` treats ALL stderr as errors — should be made less aggressive after font fix is verified
- Research Root Causes 1-3 (JSPI/FS/config_emscripten) were wrong hypotheses — the code never reached the EM_ASYNC_JS call because of the `bHaveSubstitute` gate
- JSPI IS enabled (`--enable-emscripten-jspi` in autogen.input), FS export is handled by overrides — these were never the issue

</specifics>
