# Phase 01.1: Debug Font Resolution Hook Not Firing in WASM Builds - Research

**Researched:** 2026-02-10
**Domain:** Emscripten EM_ASYNC_JS / JSPI build configuration, WASM font resolution debugging
**Confidence:** HIGH

## Summary

The font resolution hook implemented in Phase 1 is not firing in WASM builds. Research has identified **three cascading root causes**, all stemming from build configuration mismatches between what the code requires and what the current build provides. None of these are code logic bugs -- they are all configuration/plumbing issues.

**Root Cause 1 (FATAL): `EM_ASYNC_JS` used without `-sJSPI` or `-sASYNCIFY`.** The current code uses `EM_ASYNC_JS` unconditionally (the `#if HAVE_EMSCRIPTEN_JSPI` / `#else` conditional and sync fallback were removed in commit `9a046120e809`). `EM_ASYNC_JS` expands to `Asyncify.handleAsync(async () => ...)` which requires either `-sASYNCIFY` or `-sJSPI` at link time. The build has `HAVE_EMSCRIPTEN_JSPI=0` and `ENABLE_EMSCRIPTEN_JSPI=` (empty), meaning `-sJSPI` is NOT added to linker flags. `-sASYNCIFY` is also not used anywhere in the build. This means `Asyncify` is not defined at runtime, causing `em_resolveFontFromHost` to crash with a `ReferenceError` when called -- OR the linker may silently produce a broken function. Either way the hook cannot work.

**Root Cause 2 (FATAL): `"FS"` not exported for non-Qt6 builds.** The FS export was reverted in commit `0eb94818fb7a`, putting `"FS"` back inside the `$(if $(ENABLE_QT6),...)` conditional. Since `ENABLE_QT6=` (empty), `FS` is not in `EXPORTED_RUNTIME_METHODS`. The `EM_ASYNC_JS` body calls `FS.mkdirTree()` and `FS.writeFile()`, which would produce `ReferenceError: FS is not defined` at runtime. Note: with `FORCE_FILESYSTEM=1`, the `FS` module IS included in the build, but whether it is accessible inside `EM_JS`/`EM_ASYNC_JS` scope without being in `EXPORTED_RUNTIME_METHODS` is uncertain -- the Emscripten docs suggest `FORCE_FILESYSTEM` makes it available from JS but this needs empirical verification.

**Root Cause 3 (BLOCKING): `#include <config_emscripten.h>` was removed.** Commit `9a046120e809` removed the include and the `#if HAVE_EMSCRIPTEN_JSPI` / `#else` conditional, leaving only the `EM_ASYNC_JS` path. This means the code has NO sync fallback path. If the fix is to restore the JSPI conditional, the include must be restored too.

**Primary recommendation:** The fix requires three coordinated changes: (1) restore the `#if HAVE_EMSCRIPTEN_JSPI` conditional with sync `EM_JS` fallback, (2) restore `"FS"` as an unconditional export in `EXPORTED_RUNTIME_METHODS`, and (3) either enable `-sJSPI` in the build configuration OR rely on the sync `EM_JS` fallback for builds without JSPI. This is primarily a configuration restoration + verification task, not a redesign.

## Detailed Root Cause Analysis

### Root Cause 1: EM_ASYNC_JS Without JSPI or ASYNCIFY

**Confidence:** HIGH (verified from source code + Emscripten docs)

**Evidence chain:**

1. `config_host/config_emscripten.h` (generated): `#define HAVE_EMSCRIPTEN_JSPI 0` (line 13)
2. `config_host.mk` (generated): `export ENABLE_EMSCRIPTEN_JSPI=` (line 185, empty)
3. `EMSCRIPTEN_INTEL_GCC.mk` lines 33-37: `-sJSPI` is only added when `ENABLE_EMSCRIPTEN_JSPI` is `TRUE`
4. No `-sASYNCIFY` anywhere in the build system (verified by grep)
5. `fontsubst.cxx` line 74: `EM_ASYNC_JS(char*, em_resolveFontFromHost, ...)` -- used unconditionally
6. Emscripten `em_js.h`: `EM_ASYNC_JS` expands to `_EM_JS(ret, name, __asyncjs__##name, params, "{ return Asyncify.handleAsync(async () => " #__VA_ARGS__ "); }")`
7. Without `-sJSPI` or `-sASYNCIFY`, the `Asyncify` object is not defined in the Emscripten runtime

**Behavior:** The code compiles (EM_ASYNC_JS is a macro that generates a regular C function declaration + embedded JS). It likely also links (the `__asyncjs__` prefixed symbol is handled by the Emscripten linker). But at runtime, when `em_resolveFontFromHost` is called, the generated JS code references `Asyncify.handleAsync` which does not exist, producing a `ReferenceError` or similar runtime crash.

**Why the user's debugging shows the hook "not firing":** The fprintf debug statements at lines 191-192 and 228-229 WOULD fire (they are before the `em_resolveFontFromHost` call at line 241). But if `FindFontSubstitute` is being called at all, the question is whether:
- (a) The function is being called but the EMSCRIPTEN block is not reached (bHaveSubstitute is true, or s_pFontCollection is null), OR
- (b) The function is crashing at the `em_resolveFontFromHost` call silently

The debug fprintfs added in the latest commit should reveal whether (a) or (b) is happening. If the user sees "WASM FindFontSubstitute called for: X" and "WASM bHaveSubstitute=0 s_pFontCollection=0xNNNN" in stderr, but no console.warn from inside EM_ASYNC_JS, that confirms the EM_ASYNC_JS call is crashing.

### Root Cause 2: FS Not Exported

**Confidence:** HIGH (verified from source code)

**Evidence chain:**

1. `EMSCRIPTEN_INTEL_GCC.mk` line 30: `"FS"` is inside `$(if $(ENABLE_QT6),...)` conditional
2. `config_host.mk` line 234: `export ENABLE_QT6=` (empty)
3. Therefore `"FS"` is NOT in `EXPORTED_RUNTIME_METHODS`
4. The EM_ASYNC_JS body at lines 89-90 calls `FS.mkdirTree('/tmp/fonts')` and `FS.writeFile(path, ...)`

**Behavior:** Even if the EM_ASYNC_JS function could execute (Root Cause 1 fixed), the `FS.mkdirTree` and `FS.writeFile` calls would fail with `ReferenceError: FS is not defined`.

**Nuance:** `FORCE_FILESYSTEM=1` IS set in the build (line 30 of the .mk file). The Emscripten docs state: "if your C/C++ code doesn't use files but you want to use them from JavaScript, you can build with -sFORCE_FILESYSTEM which forces the full filesystem API to be supported from JS." This suggests FS MAY be accessible from JS code even without explicit export. However, this has not been empirically verified in the context of `EM_JS`/`EM_ASYNC_JS` generated code. The safest fix is to export FS unconditionally.

### Root Cause 3: JSPI Conditional and Sync Fallback Removed

**Confidence:** HIGH (verified from git diff)

**Evidence chain:**

1. Commit `9a046120e809` ("Added more logging to help debug") removed:
   - `#include <config_emscripten.h>` (line 29 of original)
   - `#if HAVE_EMSCRIPTEN_JSPI` conditional (line 72 of original)
   - The entire `#else` sync fallback block (lines 96-115 of original) using `EM_JS` + `Module.resolveSystemFontSync`
   - `#endif // HAVE_EMSCRIPTEN_JSPI` (line 117 of original)
2. This leaves ONLY `EM_ASYNC_JS` with no fallback for non-JSPI builds

**Impact:** The original Phase 1 code was correctly structured with both async and sync paths. The manual debugging inadvertently removed the sync fallback that would have worked in non-JSPI builds.

### Additional Hypothesis: FindFontSubstitute Not Being Called At All

**Confidence:** MEDIUM (plausible but debug fprintf should reveal)

It is possible that `FindFontSubstitute` is simply not being called in the WASM build. This could happen if:
- `RegisterFontSubstitutors` is not being called (the pre-match hook is never set)
- The WASM build uses a different font pipeline that bypasses `PhysicalFontCollection::FindFontFamily()`
- The fonts being tested already have a fontconfig substitute (bHaveSubstitute is true)

The fprintf debug statements at the top of `FindFontSubstitute` (commit `f1c7a055b560`) will definitively answer this. If "WASM FindFontSubstitute called for:" does NOT appear in stderr, then the issue is upstream (the function is never called).

### Additional Hypothesis: Module.resolveSystemFont Not Set

**Confidence:** MEDIUM

Even if all build issues are fixed, the host must set `Module.resolveSystemFont` before the WASM code runs font resolution. If the test environment does not set this callback, the EM_ASYNC_JS function returns 0 immediately (no font resolved). This is correct behavior (graceful fallback) but could be misinterpreted as "hook not firing."

The `console.warn('Module keys:', ...)` debug line added in commit `9a046120e809` would reveal whether the function body executes at all.

## Fix Strategy

### Fix 1: Restore JSPI Conditional + Sync Fallback (REQUIRED)

Restore the original Phase 1 code structure:

```cpp
// In fontsubst.cxx, at the top of the EMSCRIPTEN block:
#ifdef EMSCRIPTEN
#include <config_emscripten.h>   // <-- RESTORE THIS
#include <emscripten.h>
#include <set>
#include <cstdlib>
#include <unx/freetype_glyphcache.hxx>
#include <sal/log.hxx>
#endif

// ...

#ifdef EMSCRIPTEN
// ...
#if HAVE_EMSCRIPTEN_JSPI     // <-- RESTORE THIS CONDITIONAL
EM_ASYNC_JS(char*, em_resolveFontFromHost, (const char* pFamilyName), {
    // ... async version calling Module.resolveSystemFont ...
});
#else // !HAVE_EMSCRIPTEN_JSPI    // <-- RESTORE SYNC FALLBACK
EM_JS(char*, em_resolveFontFromHost, (const char* pFamilyName), {
    // ... sync version calling Module.resolveSystemFontSync ...
});
#endif // HAVE_EMSCRIPTEN_JSPI
#endif // EMSCRIPTEN
```

### Fix 2: Restore FS Export (REQUIRED)

Move `"FS"` back to unconditional export in `EMSCRIPTEN_INTEL_GCC.mk`:

```makefile
# Change from:
gb_EMSCRIPTEN_LDFLAGS += ... -s EXPORTED_RUNTIME_METHODS=[..."HEAPU32"$(if $(ENABLE_QT6),$(COMMA)"FS"...)]
# To:
gb_EMSCRIPTEN_LDFLAGS += ... -s EXPORTED_RUNTIME_METHODS=[..."HEAPU32","FS"$(if $(ENABLE_QT6),$(COMMA)"callMain"...)]
```

### Fix 3: Enable JSPI OR Validate Sync Fallback (CONDITIONAL)

Two options:
- **Option A:** Add `--enable-emscripten-jspi` to the build configuration so `-sJSPI` is added to linker flags and `HAVE_EMSCRIPTEN_JSPI=1`. This enables the async `EM_ASYNC_JS` path.
- **Option B:** Rely on the sync `EM_JS` fallback (when `HAVE_EMSCRIPTEN_JSPI=0`). The host must implement `Module.resolveSystemFontSync` instead of `Module.resolveSystemFont`. This works without JSPI.

### Fix 4: Remove Debug Code (CLEANUP)

Remove the debug fprintf statements and console.warn added during manual debugging, once the fix is verified.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| JSPI/Asyncify detection | Runtime feature detection in JS | `#if HAVE_EMSCRIPTEN_JSPI` compile-time guard | The build system already has configure-time detection. Runtime detection is fragile and unnecessary. |
| FS availability check | `typeof FS !== 'undefined'` inside EM_JS | Export FS properly in build system | Runtime checks mask configuration bugs. Fix the root cause. |
| Custom async wrapper | Hand-written `Promise` + `Suspender` | `EM_ASYNC_JS` macro (with JSPI enabled) | Emscripten handles all the JSPI plumbing automatically for EM_ASYNC_JS. |

## Common Pitfalls

### Pitfall 1: EM_ASYNC_JS Silently Requires JSPI/ASYNCIFY

**What goes wrong:** `EM_ASYNC_JS` compiles and links without error even when neither `-sJSPI` nor `-sASYNCIFY` is enabled. At runtime, the generated JS calls `Asyncify.handleAsync()` which does not exist, causing a `ReferenceError`.
**Why it happens:** `EM_ASYNC_JS` is a C preprocessor macro. It generates a function declaration and embeds JS code as data. The C compiler has no way to validate that the JS runtime environment will have `Asyncify` defined. The Emscripten linker processes the `__asyncjs__` prefix but does not appear to validate that async support is enabled.
**How to avoid:** Always guard `EM_ASYNC_JS` usage with `#if HAVE_EMSCRIPTEN_JSPI` (or check that `-sASYNCIFY` is configured). Provide an `EM_JS` sync fallback in the `#else` branch.
**Warning signs:** The `EM_ASYNC_JS` function returns 0/null for every call with no console output. Or `ReferenceError: Asyncify is not defined` in browser console.

### Pitfall 2: Removing Conditional Compilation During Debug

**What goes wrong:** While debugging, the developer removes `#if`/`#else`/`#endif` conditionals to simplify the code. This inadvertently removes a fallback path that was critical for the build configuration.
**Why it happens:** The `#if HAVE_EMSCRIPTEN_JSPI` conditional looked like it might be causing the problem (maybe the wrong branch was being compiled). Removing it to test the EM_ASYNC_JS path directly seemed like a reasonable debug step.
**How to avoid:** When debugging, add diagnostic output to BOTH branches of a conditional rather than removing the conditional. Use `#warning` or `#pragma message` to confirm which branch is being compiled.
**Warning signs:** Git diff shows removal of `#if`/`#else`/`#endif` blocks in the same commit as adding debug output.

### Pitfall 3: Reverting a Required Build Change

**What goes wrong:** The FS export was added as part of Phase 1, then reverted as a debug step (commit `0eb94818fb7a`). This revert broke a second requirement (FS availability) while investigating the first issue (hook not firing).
**Why it happens:** When a build change doesn't seem to fix the problem, it's natural to revert it. But in this case, the FS export was a separate, independently-required change.
**How to avoid:** When reverting changes during debugging, track which reverts need to be re-applied. Each Phase 1 change addresses a different requirement and they are all independently needed.
**Warning signs:** Multiple debug commits that both add and revert changes to the same files.

### Pitfall 4: config_emscripten.h Include Removal

**What goes wrong:** Removing `#include <config_emscripten.h>` means `HAVE_EMSCRIPTEN_JSPI` is not defined. If the `#if HAVE_EMSCRIPTEN_JSPI` conditional had been kept, the preprocessor would have treated the undefined macro as 0 (per C standard), which would have selected the sync `EM_JS` fallback -- actually the CORRECT path for this build. The removal of the include is redundant with the conditional removal but compounds the problem.
**How to avoid:** When removing includes, check if any macros from that header are used in conditional compilation.

## Code Examples

### Correct Code Structure (Restored from Phase 1 Plan)

```cpp
// Source: Phase 01-01-PLAN.md lines 130-187
// Location: vcl/unx/generic/fontmanager/fontsubst.cxx

#ifdef EMSCRIPTEN
#include <config_emscripten.h>
#include <emscripten.h>
#include <set>
#include <cstdlib>
#include <unx/freetype_glyphcache.hxx>
#include <sal/log.hxx>
#endif

// ... inside #ifdef EMSCRIPTEN block:

#if HAVE_EMSCRIPTEN_JSPI
// Async path: requires -sJSPI in build
EM_ASYNC_JS(char*, em_resolveFontFromHost, (const char* pFamilyName), {
    var familyName = UTF8ToString(pFamilyName);
    if (!Module.resolveSystemFont) { return 0; }
    try {
        var fontData = await Module.resolveSystemFont(familyName);
        if (!fontData || fontData.byteLength === 0) { return 0; }
        var safeName = familyName.replace(/[^a-zA-Z0-9_-]/g, '_');
        var path = '/tmp/fonts/' + safeName + '.ttf';
        try { FS.mkdirTree('/tmp/fonts'); } catch(e) {}
        FS.writeFile(path, new Uint8Array(fontData));
        return stringToNewUTF8(path);
    } catch(e) {
        console.warn('WASM font resolution failed for: ' + familyName, e);
        return 0;
    }
});

#else // !HAVE_EMSCRIPTEN_JSPI
// Sync fallback: works without JSPI. Host must implement resolveSystemFontSync.
EM_JS(char*, em_resolveFontFromHost, (const char* pFamilyName), {
    var familyName = UTF8ToString(pFamilyName);
    if (!Module.resolveSystemFontSync) { return 0; }
    var fontData = Module.resolveSystemFontSync(familyName);
    if (!fontData || fontData.byteLength === 0) { return 0; }
    var safeName = familyName.replace(/[^a-zA-Z0-9_-]/g, '_');
    var path = '/tmp/fonts/' + safeName + '.ttf';
    try { FS.mkdirTree('/tmp/fonts'); } catch(e) {}
    FS.writeFile(path, new Uint8Array(fontData));
    return stringToNewUTF8(path);
});

#endif // HAVE_EMSCRIPTEN_JSPI
```

## Open Questions

1. **Does the build actually succeed with EM_ASYNC_JS when JSPI is not enabled?**
   - What we know: The macro generates a C function declaration + embedded JS. The C compiler does not validate JS runtime requirements.
   - What's unclear: Whether the Emscripten linker catches the `__asyncjs__` prefix and errors when `-sJSPI`/`-sASYNCIFY` is not set, or silently produces broken output.
   - Recommendation: Check build logs for warnings. If it links cleanly, the failure is purely at runtime.
   - Confidence: MEDIUM -- web search suggests it compiles/links but fails at runtime.

2. **Has the user observed any stderr/console output from the debug statements?**
   - What we know: The latest commit (`f1c7a055b560`) added fprintfs that should appear in stderr if FindFontSubstitute is called at all.
   - What's unclear: The user hasn't reported what they see in the console. This output is critical for the decision tree.
   - Recommendation: The plan should start by checking if build output exists and what it shows.
   - Confidence: N/A -- depends on user input.

3. **Is `FORCE_FILESYSTEM=1` sufficient for FS access inside EM_JS/EM_ASYNC_JS?**
   - What we know: Emscripten docs say `-sFORCE_FILESYSTEM` "forces the full filesystem API to be supported from JS." The build has `FORCE_FILESYSTEM=1`. But `EXPORTED_RUNTIME_METHODS` typically controls what is accessible on the `Module` object from external JS.
   - What's unclear: Whether `EM_JS` code (which runs inside the Module closure) can access `FS` via closure scope even without it being in `EXPORTED_RUNTIME_METHODS`.
   - Recommendation: Export FS unconditionally to be safe. This has no size cost since FORCE_FILESYSTEM=1 already includes the FS code.
   - Confidence: LOW -- needs empirical verification.

4. **Should the project enable `--enable-emscripten-jspi` in the build?**
   - What we know: The build does NOT have JSPI enabled (`ENABLE_EMSCRIPTEN_JSPI=`). The Phase 1 plan assumed it would be, or at least provided the sync fallback. The sync fallback is sufficient for the immediate use case (Electron with `ipcRenderer.sendSync`).
   - What's unclear: Whether the downstream build should enable JSPI. This may have broader implications (performance, compatibility).
   - Recommendation: For now, rely on the sync fallback. Enable JSPI as a separate, deliberate decision after the basic hook works.
   - Confidence: HIGH -- the sync fallback is a well-understood alternative.
