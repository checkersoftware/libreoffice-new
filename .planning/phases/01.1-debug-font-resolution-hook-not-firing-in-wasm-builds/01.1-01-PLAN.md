<objective>
Diagnose and fix why the Phase 1 WASM font resolution hook (`em_resolveFontFromHost` via `EM_ASYNC_JS`) does not fire at runtime. The JS callback `Module.resolveSystemFont` is never called, fonts render with fallbacks, and the WASM runtime may abort with an uncaught exception.

Purpose: The Phase 1 code is structurally correct but fails at runtime for an unknown reason. This plan systematically traces the call path, adds targeted diagnostics, and fixes the root cause once identified.

Output: A working font resolution hook where `Module.resolveSystemFont` is called when a missing font is requested in the WASM build.
</objective>

**Step 1: Read and understand the current code**

Read `vcl/unx/generic/fontmanager/fontsubst.cxx` completely. Map the execution flow:

1. `RegisterFontSubstitutors()` -- sets `s_pFontCollection` and hooks
2. `FindFontSubstitute()` -- called by `PhysicalFontCollection::FindFontFamily(FontSelectPattern&)` at line 1076 of PhysicalFontCollection.cxx: `if (mpPreMatchHook && mpPreMatchHook->FindFontSubstitute(rFSD))`
3. Inside FindFontSubstitute, the EMSCRIPTEN block runs only when `!bHaveSubstitute && s_pFontCollection && font not in s_aTriedFonts`
4. `em_resolveFontFromHost()` is the EM_ASYNC_JS function that calls Module.resolveSystemFont

**Step 2: Add a diagnostic fprintf to RegisterFontSubstitutors**

Add a fprintf(stderr, ...) inside RegisterFontSubstitutors, inside the `#ifdef EMSCRIPTEN` block, right after `s_pFontCollection = pFontCollection;`:

```cpp
fprintf(stderr, "WASM RegisterFontSubstitutors: s_pFontCollection set to %p\n",
        static_cast<void*>(s_pFontCollection));
```

This confirms whether the hook registration is happening at all.

**Step 3: Add more granular diagnostics to the EMSCRIPTEN block in FindFontSubstitute**

The existing fprintf at line 191-192 prints the font name. The existing fprintf at line 228-229 prints bHaveSubstitute and s_pFontCollection. Add MORE diagnostics:

a) After the `s_aTriedFonts.find()` check (before inserting into s_aTriedFonts), add:
```cpp
fprintf(stderr, "WASM font not in tried set, will attempt JS resolution for: %s\n",
        OUStringToOString(rFontSelData.maTargetName, RTL_TEXTENCODING_UTF8).getStr());
```

b) Right before the `em_resolveFontFromHost()` call, add:
```cpp
fprintf(stderr, "WASM about to call em_resolveFontFromHost for: %s\n", aUtf8.getStr());
```

c) Right after the `em_resolveFontFromHost()` call returns, add:
```cpp
fprintf(stderr, "WASM em_resolveFontFromHost returned: %s\n", pPath ? pPath : "(null)");
```

d) Add a diagnostic INSIDE the EM_ASYNC_JS body, at the very first line (before the existing `var familyName` line):
```javascript
console.warn('em_resolveFontFromHost ENTERED for:', UTF8ToString(pFamilyName));
```

This separates "the JS function body was entered" from "Module keys were enumerated" -- if the first console.warn appears but the second doesn't, there's a crash between them.

**Step 4: Add diagnostic for the "already tried" case**

When `s_aTriedFonts` already contains the font name, add a fprintf:
```cpp
else

    fprintf(stderr, "WASM font already in tried set, skipping JS resolution for: %s\n",
            OUStringToOString(rFontSelData.maTargetName, RTL_TEXTENCODING_UTF8).getStr());
}
```

Add this as an else-clause to the `if (s_aTriedFonts.find(...) == s_aTriedFonts.end())` block.

**Step 5: Investigate JSPI_EXPORTS hypothesis**

Read `solenv/gbuild/platform/EMSCRIPTEN_INTEL_GCC.mk` lines 33-37. The current JSPI_EXPORTS list contains only `_emscripten_check_mailbox` and a mangled C++ symbol. It does NOT include `em_resolveFontFromHost` or `__asyncjs__em_resolveFontFromHost`.

According to the Phase 1 research: "No manual JSPI_EXPORTS entry needed" for EM_ASYNC_JS functions. However, this may be incorrect. The Emscripten JSPI documentation states that functions which call JS async code need to be in JSPI_EXPORTS so the JSPI runtime knows to set up a suspender.

Add a comment in fontsubst.cxx near the EM_ASYNC_JS declaration noting this hypothesis:

```cpp
// NOTE: If JSPI is enabled but em_resolveFontFromHost crashes or returns
// unexpectedly, verify that the function (or its __asyncjs__ wrapper) is
// listed in JSPI_EXPORTS in EMSCRIPTEN_INTEL_GCC.mk. EM_ASYNC_JS may
// require explicit JSPI_EXPORTS registration depending on Emscripten version.
```

Do NOT modify the .mk file (per locked decision). This is a diagnostic note for the user.
