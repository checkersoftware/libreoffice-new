# Phase 03.1: Investigate Correct Hook Point for WASM System Font Resolution - Research

**Researched:** 2026-02-12
**Domain:** LibreOffice VCL font resolution pipeline, WASM font hook placement
**Confidence:** HIGH

## Summary

The current WASM font resolution hook is placed inside `FcPreMatchSubstitution::FindFontSubstitute()` in `fontsubst.cxx`. This hook fires for **every font lookup** where the font is not already in the `PhysicalFontCollection` -- including LO's internal default/fallback fonts (Segoe UI, Lohit Hindi, etc.) and fonts that already have bundled metric-compatible substitutes (Liberation Sans, Liberation Serif, etc.). This causes two problems: (1) spurious JS calls for fonts the document does not use, and (2) system fonts replacing bundled metric-compatible fonts, causing metric mismatches and broken text layout.

The investigation reveals the root cause is structural: the PreMatchHook fires at the wrong level of abstraction. It fires during the **font fallback chain** (which tries many font names as candidates), not at the **document font request** level. The solution is NOT to move the hook to a different location in the pipeline, but rather to add filtering logic that prevents the hook from firing for fonts that should be resolved by LO's internal substitution system.

**Primary recommendation:** Keep the hook in `FindFontSubstitute` but add a guard that only allows JS resolution for fonts that are genuinely missing from the document's perspective -- by checking whether the font is a known LO default/UI font, or whether it already has a bundled metric-compatible substitute available.

## Font Resolution Pipeline (End-to-End)

### The Complete Call Chain

```
Document text with font "Calibri"
    |
    v
OutputDevice::ImplNewFont()                    [vcl/source/outdev/font.cxx:673]
    |-- Creates FontSelectPattern from vcl::Font
    |-- Calls mxFontCache->GetFontInstance(mxFontCollection, ...)
    v
ImplFontCache::GetFontInstance()               [vcl/source/font/fontcache.cxx:116]
    |-- Check cache (hash of FontSelectPattern)
    |-- If miss: pFontList->FindFontFamily(aFontSelData)
    v
PhysicalFontCollection::FindFontFamily(FSP&)   [vcl/source/font/PhysicalFontCollection.cxx:966]
    |-- For each semicolon-separated font name token:
    |   1. ImplFindFontFamilyBySearchName(normalized)  -- direct lookup
    |   2. FindMetricCompatibleFont()                  -- Arial->Liberation Sans, etc.
    |   3. StripScriptFromName() + retry
    |   4. mpPreMatchHook->FindFontSubstitute(rFSD)    *** OUR HOOK ***
    |   5. ImplFindFontFamilyBySearchName() again
    |
    |-- Second pass: retry all tokens through metric compat + PreMatchHook
    |-- Attribute-based matching (serif/sans/weight/CJK/etc.)
    |-- FontSubstConfiguration (VCL.xcu-based substitution)
    |-- Default font fallback
    v
PhysicalFontFamily found -> FindBestFontFace() -> LogicalFontInstance
```

### Key Insight: The PreMatchHook Fires Per-Token, Not Per-Document-Font

When a font like "Segoe UI" is used as the **third token** in a semicolon-separated default font list (e.g., from VCL.xcu: `"Source Han Sans SC;Noto Sans CJK SC;...;Segoe UI;Tahoma;..."`), the pipeline tries each token sequentially. Token 1 fails -> Token 2 fails -> Token 3 ("Segoe UI") reaches step 4 (PreMatchHook) -> our EMSCRIPTEN block fires -> JS call for "Segoe UI".

This is by design for desktop: fontconfig would find Segoe UI if installed on Linux. But on WASM, we're calling out to the host system for a font that LO is only looking for as one of many fallback candidates.

## Root Cause Analysis

### Problem 1: Spurious Font Requests

**Where default font names originate:**

| Font | Source | Why It's Requested |
|------|--------|--------------------|
| Segoe UI | `VCL.xcu` `/DefaultFonts/*/UI_SANS` | UI font for multiple locales; checked during style init |
| Liberation Serif | `VCL.xcu` `/DefaultFonts/*/SERIF` | Default serif for "en" locale |
| Liberation Sans | `VCL.xcu` `/DefaultFonts/*/SANS_UNICODE` | Default sans for "en" locale |
| Lohit Hindi | `VCL.xcu` `/DefaultFonts/hi-in/*` | Default for Hindi locale (CTL) |
| Source Han Sans/Serif (Chinese) | `VCL.xcu` `/DefaultFonts/zh-cn/*` | Default for Chinese locale (CJK) |

**How they reach the hook:** When a document is opened, `sw::DocumentStylePoolManager` initializes style pools with `lcl_SetDfltFont()` which calls `OutputDevice::GetDefaultFont()`. This reads font lists from VCL.xcu and creates `vcl::Font` objects with semicolon-separated family names. When the OutputDevice later tries to render text, `ImplNewFont()` runs `FindFontFamily()`, which tokenizes the name list and tries each token.

For bundled fonts (Liberation Sans/Serif/Mono), they ARE found at step 1 and never reach the hook. But for non-bundled names in the list (Segoe UI, Lohit Hindi, CJK fonts), each token reaches step 4.

### Problem 2: System Fonts Replacing Bundled Metric-Compatible Fonts

**Confidence:** HIGH (verified by code reading)

The metric-compatible font map in `PhysicalFontCollection.cxx` lines 933-950:
```
Arial          -> Liberation Sans
Times New Roman -> Liberation Serif
Courier New    -> Liberation Mono
Calibri        -> Carlito
Cambria        -> Caladea
```

When a document requests "Arial":
1. `ImplFindFontFamilyBySearchName("arial")` -- fails (Arial not bundled)
2. `FindMetricCompatibleFont()` -- maps "arial" to "liberationsans" -- **succeeds**, returns bundled Liberation Sans

So "Arial" documents correctly use Liberation Sans WITHOUT reaching the PreMatchHook. The metric-compatible system **already works correctly** for these fonts.

**However**, the problem occurs if either:
- (a) The JS hook resolves "Arial" before the metric-compatible check runs (this does NOT happen -- metric compat is at step 2, hook is at step 4)
- (b) A font name that is NOT in the metric-compatible map but IS bundled somehow gets resolved from the system

Looking at the flow again, the JS hook ONLY fires after metric-compatible check fails. So the "Liberation Sans being replaced by Arial" scenario described in the issue context would only happen if:
- "Liberation Sans" itself is requested as a target name AND
- It is NOT found in the collection (impossible if bundled) OR
- The request is for a CJK/CTL variant that includes Liberation Sans in a fallback chain

**Most likely scenario:** The font quality issue is about a different mechanism. When the document contains "Arial" explicitly and the JS hook resolves actual Arial from macOS, the system Arial has slightly different metrics than Liberation Sans. But Liberation Sans was designed to be metric-compatible with WINDOWS Arial, and macOS Arial may have minor differences from Windows Arial. So the real issue might be: macOS Arial != Windows Arial in terms of exact metrics.

**Alternative scenario:** The JS hook is resolving "Liberation Sans" itself. This could happen if:
- The document explicitly lists "Liberation Sans" as a font
- Liberation Sans IS in the collection (so the EMSCRIPTEN check `!FindFontFamily(...)` should be false)
- Unless the hook fires from the **glyph fallback path** (`FcGlyphFallbackSubstitution`), not the pre-match path

Wait -- let me reconsider. The EMSCRIPTEN block only checks `!s_pFontCollection->FindFontFamily(rFontSelData.maTargetName)`. At line 1061, `rFSD.maTargetName = aBaseFontName` is set before the hook is called. But `rFontSelData` in the hook receives the mutated `rFSD`. If `maTargetName` is "Liberation Sans" and it IS in the collection, `FindFontFamily` returns non-null and the EMSCRIPTEN block is skipped. This is correct.

**Conclusion on Problem 2:** The metric replacement problem is most likely caused by one of:
1. A font NOT in the metric-compatible map being resolved from the system when a bundled font would have been chosen by LO's fallback chain
2. The JS hook resolving a fallback candidate (e.g., "Tahoma" from VCL.xcu default list) that then gets used instead of a bundled font that would have been chosen if the fallback chain had continued

## Proposed Solutions

### Solution A: Bundled Font Whitelist (RECOMMENDED)

**Approach:** Before calling JS, check if the requested font already has a bundled substitute that would be found later in the resolution pipeline. If so, skip the JS call and let the normal pipeline handle it.

**Implementation:**
```cpp
// In the EMSCRIPTEN block of FindFontSubstitute():

// Check: is there a metric-compatible substitute already bundled?
static const std::pair<std::u16string_view, std::u16string_view> aMetricCompatMap[] = {
    { u"Times New Roman", u"Liberation Serif" },
    { u"Arial",           u"Liberation Sans" },
    { u"Arial Narrow",    u"Liberation Sans Narrow" },
    { u"Courier New",     u"Liberation Mono" },
    { u"Cambria",         u"Caladea" },
    { u"Calibri",         u"Carlito" },
};

for (auto const& [src, dst] : aMetricCompatMap) {
    if (rFontSelData.maTargetName.equalsIgnoreAsciiCase(src)) {
        // Don't resolve from JS -- let the pipeline use the bundled substitute
        goto skip_wasm_resolve;
    }
}
```

**Pros:** Simple, predictable, handles the exact metric-compatible case.
**Cons:** Duplicates the metric-compatible map from PhysicalFontCollection.cxx. Could get out of sync.

### Solution B: Skip Resolution for Fonts with Known Bundled Substitutes (BETTER)

**Approach:** Instead of duplicating the map, check if the metric-compatible substitution would succeed before calling JS.

```cpp
// Check if metric-compatible substitution would find a bundled font
vcl::font::FontSelectPattern aTmpFSD(rFontSelData);
aTmpFSD.maSearchName = GetEnglishSearchFontName(rFontSelData.maTargetName);
// Try the metric-compatible path
if (FindMetricCompatibleFont_impl(aTmpFSD)) {
    if (s_pFontCollection->FindFontFamily(aTmpFSD.maSearchName)) {
        // A metric-compatible bundled font exists -- skip JS
        return false; // fall through to normal pipeline
    }
}
```

**Problem:** `FindMetricCompatibleFont_impl` is a file-static function in `PhysicalFontCollection.cxx`, not accessible from `fontsubst.cxx`.

### Solution C: Known Default Font Blocklist (SIMPLEST, MOST EFFECTIVE)

**Approach:** Maintain a blocklist of font names that should NEVER be resolved from JS because they are LO's internal defaults. These fonts appear in EVERY document regardless of content.

```cpp
static const std::unordered_set<OUString> s_aWasmSkipFonts = {
    // LO's bundled metric-compatible fonts -- never replace with system version
    u"Liberation Sans"_ustr,
    u"Liberation Serif"_ustr,
    u"Liberation Mono"_ustr,
    u"Liberation Sans Narrow"_ustr,
    u"Caladea"_ustr,
    u"Carlito"_ustr,
    // LO internal UI/default fonts -- not needed for document rendering
    u"Segoe UI"_ustr,
    u"Tahoma"_ustr,
    // CJK defaults that are in VCL.xcu but not bundled
    // (let fontconfig handle these -- it will find a substitute)
};
```

**Pros:** Very simple, no coupling to other code, easy to maintain.
**Cons:** Static list could become stale if VCL.xcu changes.

### Solution D: Only Resolve Document-Embedded Font Names (IDEAL BUT COMPLEX)

**Approach:** Before any font resolution, extract the font names actually used in the document. Only call JS for fonts in that set.

**Problem:** This requires plumbing document font information into the VCL font resolution layer, which has no document awareness. The VCL layer only sees `FontSelectPattern` objects -- it has no way to know if a font request originated from a document style vs. an internal default.

**This is architecturally wrong for the VCL layer.** The VCL font resolution pipeline intentionally does not know about document semantics.

### Solution E: Tiered Approach -- Skip Bundled, Skip Defaults, Allow Document Fonts (RECOMMENDED)

**Approach:** Combine multiple checks:

1. **If the font IS in the collection** (current check) -- skip JS (already implemented)
2. **If the font has a metric-compatible substitute that IS in the collection** -- skip JS (new)
3. **If the font is in a known LO default/UI font list** -- skip JS (new)
4. **Otherwise** -- call JS (only truly missing document fonts)

This is the most robust solution because:
- Rule 1 prevents re-fetching already-registered fonts
- Rule 2 prevents replacing bundled metric-compatible fonts with system variants
- Rule 3 prevents spurious JS calls for LO's internal UI/default fonts
- Rule 4 ensures actual document fonts are still resolved

## Architecture Patterns

### Where the Hook SHOULD Stay

The hook should remain in `FcPreMatchSubstitution::FindFontSubstitute()`. Moving it to a different location would not solve the problem because:

1. **Moving it earlier** (before metric-compatible check): Would make the problem worse -- every font would try JS first.
2. **Moving it to document loading**: Wrong abstraction level -- VCL shouldn't know about documents.
3. **Moving it to `PhysicalFontCollection::FindFontFamily(FSP&)`**: This is the caller of the hook, not a better location.
4. **Moving it to glyph fallback**: Too late -- glyph fallback only fires after font selection is complete and a glyph is missing.

The right fix is **filtering within the existing hook**, not moving the hook.

### Recommended Code Structure

```
FindFontSubstitute(rFontSelData)
    |
    |-- [existing] IsMicrosoftSymbolEncoded / IsOpenSymbol guards
    |-- [existing] Cache check
    |
    |-- #ifdef EMSCRIPTEN
    |   |-- [existing] Already in collection? skip
    |   |-- [NEW] Has metric-compatible bundled substitute? skip
    |   |-- [NEW] Is known LO default/UI font? skip
    |   |-- [existing] In negative cache? skip
    |   |-- [existing] Call JS resolver
    |   #endif
    |
    |-- [existing] GetFcSubstitute (fontconfig)
    |-- [existing] Cache result
```

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Metric-compatible font map | Separate copy in fontsubst.cxx | Check against `aMetricCompatibleMap` from PhysicalFontCollection.cxx or replicate minimally | Single source of truth |
| Document font list extraction | Custom document parser | Not needed -- filter at VCL level using known-defaults approach | Wrong abstraction |
| Font resolution pipeline changes | New hook point | Filtering in existing hook | Preserves LO architecture |

## Common Pitfalls

### Pitfall 1: Duplicating the Metric-Compatible Map
**What goes wrong:** Creating a second copy of `aMetricCompatibleMap` that gets out of sync.
**How to avoid:** Either expose the existing map (e.g., via a static method) or use a minimal blocklist that only covers the fonts actually bundled in the WASM build.
**Warning signs:** The map in `PhysicalFontCollection.cxx` adds Bundes* fonts but the copy doesn't.

### Pitfall 2: Blocking ALL Font Resolution from JS
**What goes wrong:** An overly broad blocklist prevents legitimate document fonts from being resolved.
**How to avoid:** Only block fonts that are (a) LO internal defaults, OR (b) have bundled metric-compatible substitutes. Never block arbitrary font names.
**Warning signs:** Documents with uncommon fonts don't render correctly.

### Pitfall 3: Not Understanding the Token Loop
**What goes wrong:** Assuming the PreMatchHook fires once per font request. It actually fires per-token in a multi-token font name.
**How to avoid:** Test with multi-token font names like "Arial;Helvetica;Sans Serif".
**Warning signs:** Hook fires multiple times for what appears to be one font request.

### Pitfall 4: Quality Score Confusion
**What goes wrong:** Assuming WASM-registered fonts have the same quality as bundled fonts.
**How to avoid:** Our `registerFontFromVFS` does NOT call `IncreaseQualityBy()`. Bundled fonts get quality 4096 (from `GetDevFontList`). Fonts added via `AddTempDevFont` get 5800. Our WASM fonts get default quality (lower). This means if a WASM font and a bundled font have the same family name and same style attributes, the bundled font should win in `AddFontFace` quality comparison.
**Warning signs:** If WASM fonts somehow get higher quality, they would replace bundled fonts.

### Pitfall 5: Negative Cache Interaction
**What goes wrong:** Adding a font to the skip list but not the negative cache, causing repeated `FindFontFamily` lookups.
**How to avoid:** Skipped fonts should either be in the negative cache or checked before the negative cache check.

### Helper: Check Metric-Compatible Substitute
```cpp
// Check if the font has a bundled metric-compatible substitute
static bool hasMetricCompatibleBundledSubstitute(
    const OUString& rFamilyName,
    vcl::font::PhysicalFontCollection* pCollection)
{
    // Map: requested font -> metric-compatible bundled font
    // Mirrors PhysicalFontCollection.cxx aMetricCompatibleMap
    static const std::pair<std::u16string_view, std::u16string_view> aMap[] = {
        { u"Times New Roman", u"Liberation Serif" },
        { u"Arial",           u"Liberation Sans" },
        { u"Arial Narrow",    u"Liberation Sans Narrow" },
        { u"Courier New",     u"Liberation Mono" },
        { u"Cambria",         u"Caladea" },
        { u"Calibri",         u"Carlito" },
    };

    for (const auto& [src, dst] : aMap)
    {
        if (rFamilyName.equalsIgnoreAsciiCase(OUString(src)))
        {
            // Check if the substitute is actually bundled
            return pCollection->FindFontFamily(dst) != nullptr;
        }
    }
    return false;
}
```

### Helper: Known LO Default Fonts
```cpp
// Fonts that LO looks up as internal defaults -- never resolve from host
static bool isKnownDefaultFont(const OUString& rFamilyName)
{
    static const std::unordered_set<OUString> aDefaults = {
        // UI fonts from VCL.xcu
        u"Segoe UI"_ustr,
        u"Tahoma"_ustr,
        u"Arial Unicode MS"_ustr,
        u"Lucida Sans Unicode"_ustr,
        u"DejaVu Sans"_ustr,
        // Hindi/Devanagari defaults
        u"Lohit Hindi"_ustr,
        u"Lohit Devanagari"_ustr,
        u"Mangal"_ustr,
        // CJK defaults that trigger unnecessary JS calls
        // Note: only include fonts that are NOT useful to resolve from the host.
        // CJK fonts from the host might actually be needed for CJK documents.
    };

    return aDefaults.count(rFamilyName) > 0;
}
```

**Important note on CJK fonts:** The Chinese/Japanese/Korean default fonts (Source Han Sans, Noto Sans CJK, etc.) present a dilemma. They ARE LO defaults, but a document in Chinese genuinely needs them. The blocklist should NOT include CJK fonts if the system is meant to render CJK documents. The JS resolver should be allowed to fetch these from the host if available. Only block fonts that are purely UI-related or that have adequate bundled substitutes.

## Open Questions

1. **Exact WASM bundle contents**
   - What we know: Liberation family, Caladea, Carlito, OpenSymbol are typically bundled
   - What's unclear: Whether the specific WASM build includes all of these
   - Recommendation: Verify at runtime by checking `s_pFontCollection->FindFontFamily()` for each substitute before blocking

2. **CJK document support**
   - What we know: CJK defaults appear in VCL.xcu; they are NOT bundled
   - What's unclear: Should CJK fonts be blocked from JS resolution? This would break CJK documents.
   - Recommendation: Do NOT block CJK fonts. Only block UI fonts and fonts with bundled metric-compatible substitutes.

3. **Font quality scores for WASM-registered fonts**
   - What we know: `registerFontFromVFS` does not call `IncreaseQualityBy()`. Bundled fonts have quality 4096.
   - What's unclear: What quality do WASM-registered fonts get? Default FreeType quality is based on fontID.
   - Recommendation: Verify, and if WASM fonts could beat bundled fonts on quality, add appropriate quality management.
